1 · The mental model

There are three tokens. They are not interchangeable.

Google idToken accessToken refreshToken
Issued by Google (on the phone) Trotxi API Trotxi API
Lifetime ~1 hour 15 minutes 30 days (rotates)
Used for The body of POST /auth/google — once Authorization: Bearer … on every API call Only POST /auth/refresh and POST /auth/logout
Never sent as a Bearer header stored anywhere but secure storage sent to any other endpoint
Common confusion / mistake: pasting the Google idToken (or a masked copy) where the accessToken belongs. The API rejects it by design — audience separation means a Google token can never act as an API token.
2 · Sign-in, end to end

One round trip turns a Google identity into a Trotxi account

1
App: Google Sign-In SDK
User picks their account. SDK returns an idToken whose audience is our Web client ID (the serverClientId you configure).
2
App → POST /auth/google
Body: { "idToken": "…" }. No auth header needed — this call is how you get one.
3
API verifies cryptographically
Signature against Google's public keys, issuer = accounts.google.com, audience = our client ID. Nothing hand-made can pass — the 401 you saw on staging was this working.
4
API upserts the user
First sign-in creates the account (role commuter). Same Google account later → same user.
5
API returns { accessToken, refreshToken, user }
App saves both to flutter_secure_storage and navigates to Home. Done.
Environment note: locally (no GOOGLE_CLIENT_ID) the API runs a dev verifier that accepts JSON claims as the idToken — that's what the playground here uses. Staging runs the real Google verifier.
3 · Inside the access token

It's a signed, stateless JWT — the API trusts what's inside it

{
  "role": "commuter",      ← RBAC: what you may call
  "sub":  "<user id>",     ← who you are
  "iss":  "trotxi",         ← minted by us
  "aud":  "trotxi-api",     ← for this API only
  "exp":  now + 15 min      ← then it's a 401
}
Stateless means fast…
No DB lookup per request. The signature is the proof.
…and means role changes wait for refresh
Promote a user to driver and their old access token still says commuter for up to 15 min. You watched this live: the manifest 403'd until we refreshed. Not a bug — the design.
4 · Staying signed in

Refresh rotation — and the trap that signs out every device

1
Access token expires (15 min)
Any API call returns 401.
2
App: POST /auth/refresh
Body: the refreshToken. Response: a new accessToken and a new refreshToken.
3
The old refresh token is now dead
Rotation = the presented token is revoked, a new one issued. Always overwrite what you stored.
Replay detection — read this twice:
If an already-rotated refresh token is presented again, the API treats it as theft and revokes every session for that user. So: never retry a refresh with the same token, and if two requests 401 at once, make sure only one refresh runs — queue the rest behind it. A naive interceptor that fires two parallel refreshes will sign the rider out of everything.
5 · Sessions & sign-out

Each device is a session the rider can see and kill

Endpoint What it does
GET /me/sessions Lists this user's active sessions (one per signed-in device).
DELETE /me/sessions/:id Revokes one — that device's refresh token stops working.
POST /auth/logout Revokes the presented refreshToken. App also clears secure storage.
App rule: on logout do both — call the endpoint (server-side revoke) and TokenStorage.clearTokens(). On refresh failure (401), clear storage and route to the sign-in screen; don't loop.
6 · Reading the errors

401 vs 403 — and the traps we've already paid for

You see It means App should
401 on any endpoint No / expired / invalid access token Refresh once, retry once. Still 401 → sign-in screen.
401 on /auth/refresh Refresh token expired, rotated, or revoked Clear storage → sign-in screen. Never retry.
403 Valid token, wrong role Don't show the feature. Refreshing won't help unless the role just changed.
404 on auth paths Probably a URL bug Check the base URL — a trailing slash gave us //auth/google.
7 · The app integration contract

What the Dio interceptor must do

✓
Attach Authorization: Bearer <accessToken> to every request except /auth/*.
✓
On 401: run one refresh (mutex/queue!), overwrite both stored tokens, retry the original request once.
✓
On refresh 401: clear secure storage, go to sign-in. No loops, no replays.
✓
Store both tokens only in flutter_secure_storage — never SharedPreferences, never logs.
✓
Never log tokens — debugPrint(idToken) is in the current branch; remove it before release.

The generated client (trotxi_client) already exposes AuthApi; the interceptor is the only custom piece.
