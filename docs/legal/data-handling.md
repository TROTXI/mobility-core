# Data handling

**Owner:** Godfred Awuku · **Last updated:** 2026-09-02

**Status:** 🟡 draft. Accurate to the code as of `248ceea`. Not yet reviewed by a
lawyer, and the retention rules in the table below are proposed, not implemented.

The internal record of what personal data Trotxi holds, where it lives, why we
hold it, and who else sees it. Three things depend on this document, so it is
the one to change first when a data flow changes:

- [privacy-policy.md](privacy-policy.md), which is the public statement of the same facts
- the Apple App Privacy labels and Google Play Data Safety form ([store-submission.md](store-submission.md))
- registration with Ghana's Data Protection Commission under the Data Protection
  Act 2012 (Act 843), which asks a controller to declare its purposes and recipients

> When code and this document disagree, the code wins. Fix the document in the
> same PR, and check whether the store forms move with it.

---

## What we hold

Every table below lives in one Postgres database on Render. Column names are
real; nothing here is aspirational.

| Store                                                  | Personal data                                                              | Why we hold it                                                              | Where it comes from                                           |
| ------------------------------------------------------ | -------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `users`                                                | `display_name`, `email`, `phone`, `avatar_url`, `role`                     | Identify the rider to themselves, to the driver at boarding, and to support | Name and email from the sign-in provider; phone from Paystack |
| `auth_identity`                                        | `provider`, `provider_id`, `provider_refresh_token`                        | Match a returning sign-in to an existing account                            | Google or Apple, at sign-in                                   |
| `sessions`                                             | `refresh_token_hash`, expiry, revocation, rotation chain                   | Keep a rider signed in without storing a password, and cut off a lost phone | Generated by us                                               |
| `device_tokens`                                        | `fcm_token`, `platform`                                                    | Send the daily ask and trip notifications                                   | The app, at sign-in                                           |
| `payments`                                             | `reference`, `plan`, `amount`, `currency`, `status`                        | Prove what was charged and reconcile against Paystack                       | Paystack checkout and webhook                                 |
| `subscriptions`, `entitlement_ledger`, `credit_ledger` | Balances and movements, keyed to a user                                    | The books: what a rider bought, used, and is owed                           | Generated by us                                               |
| `reservations`                                         | Travel date, direction, pickup and drop-off stop, status, `daily_pin_hash` | Run the daily seat allocation and the boarding check                        | The rider's confirmation                                      |
| `scan_events`                                          | `rider_id`, `scanned_by`, `trip_id`, result, method                        | Audit trail for boarding disputes and fare fraud                            | The driver app at boarding                                    |
| `drivers`, `vehicles`, `trips`                         | Driver-to-trip assignment, vehicle plate, make, colour                     | Run the service and show riders which van is theirs                         | Ops                                                           |

Two entries deserve a note because they read worse than they are.

`sessions` never holds a usable token. The raw refresh token is shown to the
client once and stored only as a hash, so the table is worthless to anyone who
reads it. `reservations.daily_pin_hash` is the same idea: an HMAC-SHA256 of the
boarding code under a server-side key, never the code itself.

`auth_identity.provider_refresh_token` is the exception and the one credential we
store in a replayable form. Apple's revoke endpoint requires the token as issued,
so it cannot be hashed. It exists only to tell Apple to forget us when a rider
deletes their account, and nothing else reads it.

## What we deliberately do not hold

This section is as load-bearing as the last one. Several answers on both store
forms are "no" because of it, and each is a design choice we can lose by
accident.

**Rider location.** No part of the rider app reports where a rider is. The live
map works the other way around: the driver app publishes the vehicle's GPS to
`trip_positions`, which is keyed to a trip and has no user column at all, and the
rider app reads it. A rider's position is never sent to us, so it cannot leak
from us. Adding rider-side location later would change the answers on both store
forms and both app manifests, so treat it as a privacy change and not a feature.

**Payment credentials.** No card number, mobile-money PIN, or CVV reaches our
servers. Paystack collects those in its own checkout and hands us back a
reference. `payments.amount` and a reference is the whole of what we keep.

**Passwords.** Sign-in is Google or Apple only, so there is nothing to hash,
leak, or reset.

**Precise home or work addresses.** A reservation stores a stop id from our own
route data, not a street address a rider typed.

## Who else sees it

Each of these is a processor acting on our instructions, and each needs a data
processing agreement on file before launch. That is a gap today, listed below.

| Processor                                    | What reaches them                                                                                             | Purpose                                                             |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Render                                       | Everything in the table above                                                                                 | Hosting and the managed Postgres database                           |
| Paystack                                     | Name, email, phone, amount                                                                                    | Take payment, and mobile money is the only way most riders will pay |
| Google (Sign-In)                             | The ID token exchange                                                                                         | Prove the rider owns the Google account                             |
| Apple (Sign in with Apple)                   | The ID token exchange, and a revoke call on deletion                                                          | Prove the rider owns the Apple account                              |
| Firebase Cloud Messaging                     | `fcm_token` and the notification body                                                                         | Deliver the daily ask and trip alerts                               |
| Firebase Analytics, Crashlytics, Performance | Device model, OS version, app version, crash stacks, usage events, and Firebase's own installation identifier | Diagnose crashes and understand where riders drop out               |
| Cloudflare R2                                | Avatar images                                                                                                 | Store the photo shown on the driver's manifest                      |
| Grafana (OTEL)                               | Traces and metrics from the API                                                                               | Operational monitoring                                              |

Firebase Analytics, Crashlytics and Performance are the widest of these and the
least visible in review, because nobody wrote a line of code to turn them on.
They ship in both apps by virtue of being in `pubspec.yaml`, they start
collecting at launch, and they are why the Data Safety form cannot say we collect
nothing. Whether they should be on before a rider has agreed to anything is a
decision nobody has made yet.

## Deleting an account

`DELETE /me` runs [`AccountDeletionService`](../../services/api/src/modules/users/account-deletion.service.ts),
in a deliberate order: cut access, tell Apple, unlink providers, then erase.

- Sessions revoked and device tokens removed, so the app stops working immediately
- Apple told to revoke our access, for every Apple identity on the account
- Provider links deleted, so signing in again builds a new account rather than resurrecting the old one
- The avatar object deleted from R2
- `display_name` replaced with a placeholder; `email`, `phone` and `avatar_url` set to NULL; `deleted_at` stamped

The `users` row itself survives, and this is the part worth being able to explain
out loud. Payments and both ledgers cascade off `users`, so a hard delete would
destroy the financial record of what a person paid us. Anonymising keeps the
books balanced and attributable to an account that can no longer be connected to
a human being. What is left is a uuid and a set of amounts.

A rider asking us to delete their account also cannot be refused because a
third party is down. Apple revocation is best effort by design: if Apple is
unreachable we log nothing useful and carry on erasing, rather than abandoning
the deletion half-done with the rider's sessions already dead.

## Retention

There is no retention policy in force. Nothing expires and no job deletes
anything, so every table below grows for the life of the product. The right-hand
column is a proposal to argue with, not a description of what the code does.

| Data                      | Today                     | Proposed                                                                            |
| ------------------------- | ------------------------- | ----------------------------------------------------------------------------------- |
| `trip_positions`          | Kept forever              | 90 days. It is vehicle telemetry and stops being useful once the trip is reconciled |
| `scan_events`             | Kept forever              | 2 years, as the evidence trail for a fare dispute                                   |
| `payments`, both ledgers  | Kept forever              | 6 years, matching Ghanaian record-keeping expectations for financial records        |
| `sessions`                | Rows persist after expiry | Purge 30 days past `expires_at`                                                     |
| Anonymised `users` rows   | Kept forever              | Keep. There is no personal data left in them                                        |
| Crashlytics and Analytics | Firebase defaults         | Set explicitly rather than inherited                                                |

`trip_positions` is the one to act on first. It takes a row per GPS fix per
vehicle per trip, so it is the fastest-growing table we have and the one whose
value decays quickest.

## Known gaps

Ordered by what blocks a store submission soonest.

1. **Neither app declares any permission.** Both `AndroidManifest.xml` files and
   both `Info.plist` files are stock, with no usage description strings. The
   driver app cannot do GPS or camera scanning until this is filled in, and a
   missing or vague iOS usage string is a routine review rejection.
2. **No `PrivacyInfo.xcprivacy` in either app target.** Apple requires a privacy
   manifest declaring collected data types and required-reason API use. The pods
   ship their own; the app itself has none.
3. **No data processing agreements** with Render, Paystack, Cloudflare or Google.
4. **Not registered with Ghana's Data Protection Commission.** Act 843 requires a
   controller to register before processing, and it is a legal step rather than
   an engineering one.
5. **No retention job.** See the table above.
6. **No log redaction configured.** Nothing sets pino `redact` paths, so it is
   worth confirming what reaches the logs before deciding it is fine.
7. **No consent model for analytics.** Firebase starts collecting at launch.
8. **No privacy policy link or terms acceptance in either app.** Both stores want
   a reachable policy URL, and the app should link it from the profile screen.
