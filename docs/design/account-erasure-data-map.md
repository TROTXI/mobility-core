# Account deletion: store-by-store evidence and limits

Status: pilot implementation review, 29 September 2026. This inventory is
about the **replacement** backend and its current app integrations. A `204`
from `DELETE /v1/me` means local account closure committed. It does **not**
certify that every copy held by an external provider or database backup has
been removed. This document does not set a new statutory retention period.

## Machine-readable result and operational sequence

`app.account_erasures` is the immutable local-closure fact. The read-only
`app.account_erasure_status` view combines it with `app.erasure_tasks` and
reports `tracked_complete`, `pending`, or `retry_needed`, plus task counts.
It contains no profile, payment amount or provider reference. The label
`tracked_complete` is limited to the **tracked avatar and revocable-grant
tasks**. It is not a cross-provider erasure certificate.

To handle a verified request: record the request and account ID securely; run
the authenticated account deletion; inspect the status view; run the existing
`erasures` maintenance job if tasks are pending/unavailable; inspect its
durable start/outcome rows and the status view again; then review retained
financial/incident evidence and external-provider requests separately. Never
record a task as done because an API returned `204` or a provider was
unreachable. Do not put raw phone numbers, email addresses, OTPs, provider
payloads or exact coordinates into job logs.

## What remains open under issue #284

- The provisional accounting period and production financial-evidence policy
  still need Ghana counsel approval; the implemented 180-day raw-body rule
  holds open financial work and never deletes provider references.
- Verified provider-side deletion/retention procedures for Resend, mNotify,
  Firebase diagnostics, Grafana and Render backups. The backend does not have
  the identifiers or provider workflow needed to claim those are complete.
- The Ops website now shows the restricted local status view, explicitly
  labelled as local and tracked cleanup only.
- The manual staging cadence is in `account-erasure-retention-policy.md`;
  unattended production schedules and alerts are still not active.

These are explicit limits, not reasons to relabel local account closure as
complete erasure across every store.

Use the [operations checklist](account-erasure-operations-checklist.md) for
the restricted evidence packet, provider register and backup inventory.
Its restore release gate explicitly records that independent deletion-fact
capture and a restore-specific replay tool are not yet implemented.
